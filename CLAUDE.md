# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`wp-rest-cli` is a WP-CLI-style command line tool that talks to **any** WordPress site's REST API over plain HTTP — no PHP, no SSH, no local WordPress install. It auto-discovers a site's REST API from just a URL, introspects routes the way `?_method=OPTIONS` does, and speaks WP-CLI's own `--format=`/`--fields=` conventions. It's an independent reimplementation inspired by `wp-cli/restful`, not a WP-CLI plugin — everything happens over HTTP against a real site.

## Commands

```sh
npm run wp -- <namespace> <route> [<verb>] [<id>] [--flag=value...] --url=<site>  # run against src/ via tsx, no build needed
npm run build          # bundle to dist/cli.js (tsup)
npm run dev             # tsup --watch
npm test                 # jest (unit, via wp-scripts) + vitest run (an execa-driven integration suite against a local fixture server)
npm run test:unit        # wp-scripts test-unit-js (jest), unit suite only
npm run test:integration # vitest run, integration suite only
npm run test:watch       # wp-scripts test-unit-js --watch (unit only; see test:integration:watch for the integration suite)
npm run typecheck       # tsc --noEmit
npm run lint            # wp-scripts lint-js (WordPress/Gutenberg coding standards, via @wordpress/eslint-plugin)
npm run lint:pkg-json   # wp-scripts lint-pkg-json (validates package.json, via npm-package-json-lint)
npm run format          # wp-scripts format (WordPress/Gutenberg coding standards, via @wordpress/prettier-config)
```

Run a single unit test file: `NODE_OPTIONS=--experimental-vm-modules npx wp-scripts test-unit-js formatter.test.ts`. Run a single unit test by name: `NODE_OPTIONS=--experimental-vm-modules npx wp-scripts test-unit-js -t "name substring"`. The integration suite (`test/integration/cli.test.ts`) spawns the CLI via `execa`/`tsx` against an in-process HTTP fixture server (`test/integration/fixtures/server.ts`), so it's slower (seconds, not ms) than the unit tests — expect that when iterating. Run just that suite with `npx vitest run test/integration/cli.test.ts` or `npx vitest run -t "name substring"`.

### Coding standards

This project follows WordPress/Gutenberg JavaScript coding standards, enforced via `@wordpress/scripts`:

- `eslint.config.js` spreads `@wordpress/eslint-plugin`'s flat `recommended` config (which itself pulls in `@wordpress/prettier-config`-aware formatting rules and TypeScript support via `typescript-eslint`, since both `prettier` and `typescript` are installed). Project-specific overrides on top: a `_`-prefixed-arg allowance for `@typescript-eslint/no-unused-vars`, and `no-console: off` for `src/cli.ts`/`src/core/debug.ts` (a CLI's whole job is printing).
- `.prettierrc.cjs` re-exports `@wordpress/prettier-config` as-is (tabs, single quotes, `printWidth: 80`). `prettier` itself is aliased to `npm:wp-prettier` (WordPress's own Prettier fork) in `devDependencies`, since `wp-scripts format`/`lint-js` require that exact package to be installed under the `prettier` name — a plain `prettier` install will not satisfy them.
- `.npmpackagejsonlintrc.json` extends `@wordpress/npm-package-json-lint-config` (used by `npm run lint:pkg-json`) but overrides `valid-values-license` to allow `MIT` — the WordPress default expects `GPL-2.0-or-later`, which fits a WP plugin but not this project (an independent, MIT-licensed CLI tool, not a WP-CLI plugin — see "What this is" above).
- `.prettierignore` excludes `.github/`, `*.yml`/`*.yaml`, and `mkdocs.yml` — the WordPress formatting/tab-indent rules apply to this project's JS/TS/JSON, not to CI workflow or docs-site YAML.
- JSDoc is required on functions (`jsdoc/require-param` etc., from the WordPress config) — see the existing `src/` files for the expected style (a one-line summary, `@param`/`@return` with real descriptions, not bare tags).

## Architecture

### Command grammar and dispatch

The whole CLI is one dynamic grammar, not a fixed command tree:

```text
wp                                                              # list namespaces
wp <namespace>                                                  # list routes under that namespace
wp <namespace> <route>                                          # introspect: methods/args/context via OPTIONS
wp <namespace> <route> list|get|create|update|delete|exists|generate [...]
wp <namespace> <route> meta <add|clean-duplicates|delete|get|list|patch|pluck|update> ...
wp help [<namespace> [<route...> [<verb>]]]                     # same shapes, but never performs the request
wp config get|set|clear|rotate-key
wp auth <type> login|add|list|remove|use|status         # <type>: application-passwords | oauth2
```

- `src/cli.ts` is the Commander entry point. It only owns a fixed set of long flags (`KNOWN_LONG_FLAGS`); any other `--name=value` or bare `--flag` is rewritten by `normalizeDynamicFlags` into a positional `name=value` token before Commander sees it, because those are dynamic WordPress field/query args whose names aren't known ahead of time (e.g. `--per_page=5`, `--title=`, `--force`). `config`, `auth`, and `help` are intercepted as special first-argument subcommands before the rest of the positional args reach the main dispatch.
- `src/commands/rest.ts` is the core dispatcher: `parseCommandArgs`/`parseHelpArgs` turn the raw positional args into a `ParsedCommand`/`ParsedHelp`, and `runRestCommand`/`runHelpCommand` execute them.
- **Route parsing is intentionally loose**: `consumeRouteSegments` greedily consumes leading tokens as `/`-joined route segments until it hits a recognized verb, the literal `meta` keyword, or a `field=value`-shaped token. This lets a WordPress route that's nested under several literal path segments (e.g. `WP_REST_Global_Styles_Controller`'s `global-styles/themes/(?P<stylesheet>%s)`) be addressed as separate CLI words (`wp wp/v2 global-styles themes get <stylesheet>`), the same way WP-CLI addresses nested commands. A consequence: a genuinely unrecognized verb-position token is no longer rejected locally — it's folded into the route and left to fail naturally as a live 404 from the API, rather than a local "unknown verb" error.
- **Routes are discoverable level-by-level, not just addressable once known**: `core/indexer.ts`'s `routeChildren` groups a namespace's routes by their next `/`-segment beneath whatever prefix has been typed so far, to arbitrary depth. `wp <namespace>` (empty prefix) and bare `wp <namespace> <route>` introspection both consult it before falling through to `resolveRouteInfo`/schema introspection — if the typed prefix has further segments underneath it, the child segments are listed instead (a pure-container child that isn't itself a route is marked `(subcommand)`). This means a route like `global-styles/themes` doesn't have to be typed in full to be found: `wp wp/v2` → `wp wp/v2 global-styles` → `wp wp/v2 global-styles themes` each reveal the next step, the same way WP-CLI's own nested commands (`wp post meta ...`) are explored one word at a time. `wp help <namespace> [<route...>]` mirrors this exactly. A namespace where every route is a single segment (the common case) is unaffected — `routeChildren` at the root just lists each route once, same as before. A route can be a **"hybrid"** — both directly addressable *and* a container for further children (e.g. once a `variations` child is registered beneath the already-addressable `global-styles/themes`) — `runRestCommand`/`runHelpCommand` check `isRealRoute` before deciding whether bare introspection should show the route's own schema or just its children; a hybrid gets its own schema plus a `renderChildrenNote` listing appended.
- **A route's URL parameter isn't always at the end**: `core/indexer.ts`'s `splitPlaceholder` finds a single `(?P<name>...)` placeholder *anywhere* in a route's path (not just trailing) and reports both the route's literal segments with it removed and the position it belongs at (`paramIndex`). This is how e.g. real WordPress's `/wp/v2/posts/(?P<parent>[\d]+)/revisions` (parameter in the middle) becomes CLI-addressable as `wp wp/v2 posts revisions get <parent>` — `routesForNamespace`/`resolveRouteInfo` use the joined literal segments (`posts/revisions`) as the route name, `supportedVerbsForRoute` adds `get`/`exists` to it (in addition to whatever collection verb it already has) since it needs a value to be addressed at all, and `core/verbs.ts`'s `buildVerbRequest` splices the id back into `route.split('/')` at `paramIndex` (defaulting to the end, matching every route this CLI supported before mid-path parameters existed) rather than always appending it. A path with more than one placeholder (e.g. one specific revision, needing both a parent post id and a revision id) isn't addressable by this CLI's single-`<id>` grammar and stays invisible, same as before.
- `verb`/`get`/`update`/`delete`/`exists` require an `<id>` as the first token after the verb; `list`/`create`/`generate` don't, and treat everything after the verb as `field=value` pairs.

### Layering under the dispatcher

- `core/discovery.ts` — resolves a bare site URL to its REST API root: `HEAD` for the `Link: <...>; rel="https://api.w.org/"` header → GET + HTML `<link>` tag fallback → probe `/wp-json/` → probe `/?rest_route=/`.
- `core/indexer.ts` — fetches the site's root index (`fetchIndex`) and derives the route list for a namespace (`routesForNamespace`). Routes registered only in parameterized form with no bare collection sibling (like the global-styles/themes example above) are still listed, by their base path with the trailing `(?P<...>)` segment stripped — `resolveRouteInfo` is what later tells the rest of the code that such a route needs a real OPTIONS request against an *instantiated* URL (or a fallback to the index's own embedded schema) rather than the bare collection path, which would 404.
- `core/introspect.ts` — `introspectRoute` does the live OPTIONS request; `supportedContexts` reads the `context` enum out of the resulting schema.
- `core/verbs.ts` — `buildVerbRequest` maps a `SingleRequestVerb` (`list`/`get`/`create`/`update`/`delete`/`exists` — i.e. every verb *except* `generate`, which isn't a single HTTP request) plus id/fields/content into a `{method, url, body}`. `generate` is handled entirely in `rest.ts` as a loop of `create` calls; `exists` reuses `get`'s request shape but is interpreted specially by the caller (404 → exit 1, not an error).
- `core/validate.ts` — `validateFieldTypes`, called from `rest.ts`'s `validateVerbFields` before a `list`/`create`/`update`/`generate` request is sent, catches two kinds of problem locally against the route's live arg schema: a `field=value` whose value doesn't match its declared JSON Schema type (e.g. `--per_page=abc` for an `integer` arg), and — only when its `checkRequired` param is set — a `required` arg missing from `fields` altogether. `validateVerbFields` passes `checkRequired: true` for every verb except `update`: `list`/`create`/`generate` all map onto that verb's *own* live schema (see `COLLECTION_VERB_METHOD` below), where a declared `required` genuinely applies — but `update` borrows `create`'s POST schema (WordPress exposes no separate schema for the item-level PUT endpoint), and a partial update legitimately omits those create-time required fields, so it alone is exempt.
- `core/formatter.ts` — `formatOutput` renders a response body per `--format` (`table`/`json`/`csv`/`yaml`/`ids`/`count`/`raw`), including `--fields`/`--field` selection and dot-flattening nested objects for table/csv. Table cells are sanitized of control characters the `table` package rejects (real post content routinely contains raw `\t`/`\r`).
- `core/client.ts` — thin `fetch` wrapper (`WpRestClient`) that attaches auth headers and turns non-2xx responses into a `WpApiError`.
- `core/errors.ts` — `WpApiError` (parsed `{code,message,data}` from the REST API) vs `CliError` (the CLI's own local validation failures); `formatErrorForDisplay` is what the top-level catch in `cli.ts` prints.
- `core/auth/` — `AuthProvider` interface with two implementations: `BasicAuthProvider` (username/password or WordPress Application Password over HTTP Basic Auth) and `OAuth2AuthProvider` (a bearer token, via the WP-API/OAuth2 plugin). Built as an interface so each auth mechanism stays independent of request-building code. `core/auth/types.ts` holds the `wp auth <type> ...` registry one layer up from `AuthProvider`: `APPLICATION_PASSWORDS_AUTH_TYPE`/`OAUTH2_AUTH_TYPE` (the literal keys, matching WordPress's/the plugin's own root-index `authentication` keys — see below) and the two-member `AuthType` union. `core/auth/authorize.ts` implements the browser-based Application Password *registration* flow used by `wp auth application-passwords login`: it reads the authorization endpoint the site's root index advertises (`core/indexer.ts`'s `getApplicationPasswordAuthorizationUrl`), starts a short-lived `node:http` server on an OS-assigned `127.0.0.1` port, prints the resulting `/wp-admin/authorize-application.php?...&success_url=http://127.0.0.1:<port>/callback` URL for the user to open, and resolves once WordPress's redirect hits that callback with the new `user_login`/`password` — no auth is needed to run this flow itself (approval happens in the user's own browser session). It also exports `canSiteUseApplicationPasswords(apiRoot)` (WordPress requires HTTPS, except on `localhost`/`127.0.0.1`/`[::1]`), the single shared source of truth for that rule — `login` uses it to fail fast with a targeted error (pointing at `wp auth application-passwords add` as a fallback) before ever starting the browser flow; `add` (below) uses the same function to skip a doomed-to-fail verification call on a plain-HTTP, non-loopback site. `core/auth/application-passwords.ts` has two further primitives, both used *after* a credential exists rather than during the browser flow itself: `introspectApplicationPassword` (GETs `wp/v2/users/me/application-passwords/introspect` — returns that credential's own `uuid` if it really is an Application Password, `undefined` for anything else, never throws) and `revokeApplicationPassword` (`DELETE`s the single-uuid route only — **never** the bulk `wp/v2/users/me/application-passwords` route, which would revoke *every* Application Password the user has — also never throws, resolves `false` on any failure).
    - `core/auth/oauth2.ts` implements OAuth2 (WP-API/OAuth2 plugin): `runOAuth2AuthorizationCodeFlow` (browser flow, `wp auth oauth2 login`) and `fetchOAuth2ClientCredentialsToken` (no browser, `wp auth oauth2 add`) both call a single shared gate, `assertOAuth2Supported`, first — it refuses to attempt anything (no browser tab, no local server, no token request) against a site that's plain-HTTP-and-non-loopback (reusing `canSiteUseApplicationPasswords`; RFC 6749 requires TLS here even though the plugin itself doesn't enforce it) or that doesn't advertise a `token` endpoint in its index at all. **Discovery/gating deliberately never checks the index's `grant_types` array for `client_credentials`** — the plugin only ever populates `grant_types` from its browser-authorize handlers (`authorization_code`/`implicit`), never from the token endpoint's separate `client_credentials` special case, so a real site can support `client_credentials` while never listing it there; `core/indexer.ts`'s `isOAuth2Supported`/`getOAuth2Endpoints` key off `endpoints.token` presence only. Unlike Application Passwords' OS-assigned ephemeral callback port, `login`'s local callback server binds to a **fixed** address (`defaultOAuth2RedirectUri`, default `http://127.0.0.1:8787/callback`, overridable via `port=`/`redirect-uri=` fields) — the plugin matches a client's registered redirect URI exactly, so it has to be known (and the same, every run) *before* the OAuth2 "Application" is created. That creation step itself (`client_id`/`client_secret`/redirect URI, in wp-admin's Users → Applications) has **no self-service equivalent** the way Application Passwords' `authorize-application.php` does — `login`/`add` both require a pre-existing `client_id` the user obtained by hand. The plugin also has no refresh-token grant and exposes no REST revocation endpoint, so `StoredOAuth2Credential` (`config.ts`) never expires locally and `oauth2 remove` only ever forgets a credential, never revokes it. `wp auth oauth2 add` also accepts a third, simpler credential shape — a personal access token generated by hand in wp-admin (no client/Application involved at all) — via `--token`, mutually exclusive with `--client-id`/`--client-secret`; this path skips `assertOAuth2Supported` entirely (a personal token needs no token-endpoint support to be discovered, only the same plain-HTTP/loopback TLS check reused via `canSiteUseApplicationPasswords`) and is verified with its own `verifyPersonalToken` helper (`commands/auth/oauth2.ts`) — unlike `client_credentials`' token (user id 0, so verification only ever warns), a personal token authenticates as a real user, so an unambiguous 401/403 blocks the save unless `skip-verify=true` is passed. Stored as `grantType: 'personal_token'` with no `clientId` (`StoredOAuth2Credential.clientId` is optional for this reason).
- `src/commands/auth.ts` is a thin entry point: `parseAuthArgs` validates `<type>` (via `assertKnownAuthType`) before parsing the verb, and the shared `ParsedAuth` union/`runAuthCommand` dispatcher live here. Since `AuthType` is a real two-member union, TypeScript's exhaustiveness check on `runAuthCommand`'s `switch (parsed.authType)` forces a compile error the moment a further type is added without a matching case — the extension point for a future auth mechanism is enforced by the type system, not just a comment. Per-type command handlers live in `src/commands/auth/application-passwords.ts` and `src/commands/auth/oauth2.ts` (the file was split into this directory once a second type actually existed — see the git history for the single-file version if useful context). `--client-id`/`--client-secret`/`--token` are real global flags (registered in `cli.ts` and carried on `GlobalFlags`), not field tokens — they're the actual credential, so `oauth2 login`/`add` read them straight off `flags` at handler-execution time (in `commands/auth/oauth2.ts`) the exact same way `application-passwords add` already reads `--username`/`--password`, rather than through `ParsedAuth`. `redirect-uri=`/`port=` (login-only, both optional overrides of the fixed callback address) and oauth2 `add`'s own `skip-verify=` (mutually exclusive with nothing — it only ever applies to the `--token` path, since `client_credentials`' verification never blocks in the first place) stay as inline field tokens (matching the existing `app-name=`/`skip-verify=`/`all=` convention), since they're meaningful only inside that one subcommand and don't warrant CLI-wide flag surface. `parseLoginArgs`/`parseAddArgs` reject the old `client-id=`/`client-secret=` field-token spelling explicitly (a pre-`--client-id`/`--client-secret` design) with a migration-hint error, rather than silently capturing and ignoring it. The positional `<url>` on `login`/`add`/`remove`/`use` (for both types) is itself optional — `resolveAuthUrlArgument` falls back to a `defaultUrl` param (`cli.ts`'s auth dispatch passes `flags.url ?? getDefaultUrl()`, the same precedence the generic REST pipeline already uses for its own `siteUrl`) whenever the next token is missing or shaped like one of the subcommand's own known fields rather than a URL, so a command doesn't force repeating a site the CLI was already invoked with (e.g. `wp --url=<site> auth oauth2 login --client-id=<id>`). An explicit positional `<url>` still wins over the fallback.
- `src/config.ts` — persists `--url`/`--username` defaults on disk via `conf` (`wp config get|set|clear`), encrypted at rest with a random key generated once per machine and stored in its own file (`credential-key`, alongside the config data, mode `0o600`) rather than a fixed key shipped in source — protects a copied/leaked config file alone, not against something with full read access to the same account (an OS keychain would be needed for that; deliberately out of scope, to avoid a native-binding dependency and Linux-headless/CI availability issues). `rotateEncryptionKey()` (`wp config rotate-key`) regenerates that key and re-encrypts the existing store under it — an incident-response escape hatch, not something normal operation needs (note it round-trips the store raw and doesn't go through the migration below, so a legacy-shape entry can persist through a rotation until that site is next read/written). Also persists per-site credentials in a `sites` map keyed by `normalizeSiteUrl(url)`, one `PerSiteCredentials` record per site holding **both** an `application-passwords` and an `oauth2` sub-entry at once — `getSiteCredential`/`setSiteCredential`/`removeSiteCredential` all take an explicit `authType` argument (via overloads) and only ever touch that one sub-key, never the other type's credential for the same site. A private `readSites()` helper transparently migrates the old, pre-multi-type flat shape (a credential's fields directly on the `sites[url]` entry) into the new nested shape on every read — writes always produce the new shape, so migration only ever has to handle what an older version of this tool already wrote. `listSiteCredentials()` stays type-agnostic (one row per stored `(url, authType)` pair, as a `SiteCredentialRow` discriminated union) rather than taking a filter parameter; each type's own `list` handler filters client-side. Neither a stored Application Password's `uuid` nor an OAuth2 credential's `accessToken` (nor a `clientSecret`, which is never persisted at all — see `core/auth/oauth2.ts` above) ever appears in that output. Managed via `src/commands/auth.ts`'s `wp auth <type> login|add|list|remove|use|status` (dispatched from `cli.ts` the same way `config` is, before the generic REST pipeline); `remove --all` is scoped to its own auth type only — it never touches the other type's credential for the same site. `clearDefaults()` (`wp config clear`) only clears the default `--url`/`--username`, not `sites`. `application-passwords remove`/`remove --all` attempt to revoke a credential on the site first (best-effort, swallowing every failure) whenever a `uuid` is on record; `login` does the same to the *previous* credential for a site it's about to replace, always after the new one is safely stored first. `application-passwords add` verifies a manually-supplied credential before saving unless `--skip-verify` is passed: it tries `introspectApplicationPassword` first (conclusive either way), falling back to a plain authenticated `GET wp/v2/users/me` that only *blocks* the save on an unambiguous 401/403. `commands/rest.ts`'s `buildAuth` is an explicit switch on `--use-auth` first (env vars/a stored credential are only ever consulted in the `'env'`/undefined branch) — with neither `--use-auth` nor `--username`/`--password`/env vars given, both an application-passwords *and* an oauth2 credential stored for the same site is a fail-fast `CliError` naming both `--use-auth` values, not a silent preference for one.

### `meta` commands (`src/commands/meta.ts`)

WP-CLI's `wp post meta` talks to `wp_postmeta` directly. Over REST there's no such table access — meta only exists as the `meta` object field on the parent resource (visible only for keys registered with `show_in_rest`), read via `GET` and written by `PATCH`ing `{meta: {...}}` onto the resource. Every one of the 8 subcommands (`add`/`clean-duplicates`/`delete`/`get`/`list`/`patch`/`pluck`/`update`) is a best-effort mapping onto that model rather than a literal port — notably `add` behaves identically to `update` (REST has no multi-value "add"), and `clean-duplicates` only does anything for array-type (`single: false`) fields. `patch`/`pluck` do client-side key-path traversal on the fetched value (see `getAtPath`/`setAtPath`/`deleteAtPath`) since REST has no partial-update endpoint for nested structures. `meta`'s own full 8-subcommand usage synopsis (`printMetaUsage`) is only shown for a route whose create/update schema actually declares a `meta` arg (`routeSupportsMeta`), and only via `wp <namespace> <route> meta`/`wp help ... meta` directly — bare route introspection doesn't repeat it, since `meta` already shows up there as a discoverable subcommand (see `withMetaChild`/`renderChildrenNote` above); running it there too was pure noise on every route that supports meta.

### Help output

Two independent renderers in `rest.ts` cover a route/verb's help, both built dynamically from the *live* introspected schema (not a hardcoded field list the way WP-CLI's own `wp post create` synopsis is) — so the exact flags shown differ per site and per route:

- `renderRouteHelp`/`printVerbHelp` render the dense `usage: ... \n   or: ...` synopsis block. This is what `wp help <namespace> <route> [<verb>]` uses.
- `renderRouteHelpWpCli`/`renderVerbHelpWpCli` render a NAME/DESCRIPTION/SYNOPSIS/SUBCOMMANDS (or .../OPTIONS/EXAMPLES) page matching real WP-CLI's own `--help` output — e.g. `wp post --help`/`wp post create --help`. This is what a trailing `--help`/`-h` flag on any `<namespace> <route> [<verb>]` command triggers. Since arbitrary REST routes have no per-command description text the way WP-CLI's hardcoded commands do, the DESCRIPTION/SUBCOMMANDS text is templated from the verb and route names (`VERB_DESCRIPTIONS` in `rest.ts`) rather than pulled from the schema. `formatEndpointArgs` (the detailed per-arg listing both renderers embed) also follows real WP-CLI's own OPTIONS convention: `[--name=<type>]` (bare, no brackets, if required) with the description indented beneath and a `---`-delimited `default:`/`options:` block when the schema declares them — `<type>` rather than the arg name is the placeholder, since unlike a real WP-CLI command this route's fields aren't known ahead of time.

Both renderers share `runHelpCommand`, which takes a `style: HelpStyle` param (`'usage'` default, `'wpcli'` for `--help`) to pick between them for `'route'`/`'verb'` modes. In `cli.ts`, `--help` is *not* Commander's automatic help option — `program.helpOption(false)` disables that, and an explicit `-h, --help` boolean option is registered instead, so the action handler can detect it (`options.help`) and dispatch through the same `parseHelpArgs`/`runHelpCommand` pipeline `wp help ...` uses, just with `style: 'wpcli'`; `wp help ...` itself always keeps `style: 'usage'` even if a redundant `--help` is also passed. `update`/`generate`'s argument list (in both renderers) is borrowed from the `create` (POST) schema as the closest available approximation, since the item-level PUT endpoint's schema isn't exposed by the collection's OPTIONS response.

A *list of child items* (as opposed to a single route/verb's own args) is a separate case from the above and isn't gated behind `--help` at all: for `--format=table`, every level renders WP-CLI's own row style (`formatSubcommandRows`: each label padded out to the widest one plus a fixed gap, then its supported verbs as the "description" — there's no real per-namespace/per-route text to show) instead of an ASCII table —

- The top-level bare `wp`/`wp help` (namespaces) and bare `wp <namespace>`/`wp help <namespace>` (routes) wrap those rows in a full NAME/DESCRIPTION/SYNOPSIS/SUBCOMMANDS page (`renderChildListWpCli`), mirroring what real WP-CLI's own bare `wp` prints.
- A *pure container* route — one with no schema of its own, only deeper routes registered beneath it (`children.length > 0 && !isRealRoute(...)`, e.g. `wp/v2 global-styles` before its `themes` child is instantiated) — gets the same NAME/DESCRIPTION/SYNOPSIS/SUBCOMMANDS wrapper, one level deeper.
- A *hybrid* route's nested-children note (`renderChildrenNote`, appended after its own regular schema output — see `routeChildren` above) reuses just the row style, with no NAME/DESCRIPTION/SYNOPSIS headers, since it's appended to output that already has those.

Any other `--format` keeps returning the plain `{route, verbs}` rows (`buildChildRows`/`renderRouteChildren`) at every level instead, since those are consumed by scripts, not read as a page.

### Testing conventions

- Unit tests (`test/unit/`), run under **Jest** (ESM via `ts-jest`, config in `jest.config.js`), test pure logic (parsing, formatting, indexer route-matching) with no network. Jest's ESM setup here can't hoist `jest.mock()` module replacement the way Vitest's `vi.mock()` did — a future test needing to mock one of this project's own modules would need `jest.unstable_mockModule()` plus a dynamic `import()`.
- The integration suite (`test/integration/cli.test.ts`), run under **Vitest** (`vitest.config.ts` now scopes it to `test/integration/**`), is the source of truth for end-to-end CLI behavior: it starts `test/integration/fixtures/server.ts` (a plain `node:http` server modeling a `wp/v2` index, a `widgets` collection with full CRUD + `meta`, and a parameterized-only `global-styles/themes` route) and drives the actual CLI binary via `execa` + `tsx`. When adding a new verb/command, prefer extending this fixture and adding an integration test over mocking `fetch` at the unit level, since most of the value here is in the URL-building and dispatch logic across the whole pipeline.
