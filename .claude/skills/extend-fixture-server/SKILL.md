# Working with `test/integration/fixtures/server.ts`

## Why this exists

The integration suite (five files, split by profiled time so Vitest can run them roughly evenly in parallel: `cli-core.test.ts`, `cli-core-routing.test.ts`, `cli-meta.test.ts`, `cli-auth.test.ts`, `cli-auth-oauth2.test.ts`) doesn't hit a real WordPress site — each file spins up its own plain `node:http` server that plays the part of one, then drives the **actual built CLI** (`dist/cli.js`) against it via the shared `runCli` helper (`test/integration/fixtures/run-cli.ts`, wrapping `execa('node', [distCliEntry, ...args, ...])`). This is the source of truth for "does the whole pipeline actually work" (URL building, discovery, OPTIONS introspection, dispatch, formatting) — prefer extending this over mocking `fetch` in a unit test, since most bugs in this codebase are about how the pieces connect, not about any single function's logic in isolation.

The fixture currently models:
- `/wp-json/` — the root index, listing `namespaces: ['wp/v2']` and a `routes` map. Note real WordPress's actual root index is much larger (it embeds full per-route schemas); this fixture keeps `routes` entries minimal (`methods` + a bare `endpoints` skeleton) and relies on a separate OPTIONS handler for full schema — mirroring how `core/indexer.ts`'s `getRouteSchema` normally prefers a live OPTIONS request over the index's own (thinner, in this fixture) schema, falling back to the index only for the parameterized-only-route case.
- `/wp-json/wp/v2/widgets` — a full CRUD collection (GET/POST) + item (GET/PUT/DELETE) resource, with a `meta` field (object, with `color`/`tags` as example registered keys) so it doubles as the fixture for `meta` subcommand tests.
- `/wp-json/wp/v2/global-styles/themes/(?P<stylesheet>%s)` — modeled on `WP_REST_Global_Styles_Controller`: registered **only** in parameterized form, no bare collection at all, GET-only. This is what exercises `resolveRouteInfo`'s "requires a URL parameter" path and the multi-segment route parsing (`wp/v2 global-styles themes get <stylesheet>`).
- `/wp-json/wp/v2/users/me`, `/wp-json/wp/v2/users/me/application-passwords/introspect`, and `DELETE /wp-json/wp/v2/users/me/application-passwords/:uuid` — model `wrapido auth application-passwords add`'s credential verification and `wrapido auth application-passwords remove`'s server-side revocation. These are the fixture's only routes that actually inspect the incoming `Authorization` header (via the shared `parseBasicAuth(req)` helper) rather than ignoring auth entirely like every other route here — see them for the pattern if a new fixture route needs to behave differently depending on the credential sent, rather than just the URL/method. Revoked uuids are tracked in a module-scope `Set` exposed via an exported getter (`getRevokedApplicationPasswordUuids()`) rather than a property on the returned `Fixture` — the established pattern for letting a test inspect fixture-internal state that isn't part of any HTTP response.

## Adding a new fixture resource or behavior

1. Add the route's entry to the `routes` map in the `/wp-json/` handler (namespace, `methods`, and a plausible `endpoints` skeleton — this is what shows up in `wrapido <namespace>`'s route listing).
2. If the route needs full schema (arg names, types, `required`, `enum`, `default`, `description`) for introspection/help tests, add an `OPTIONS` handler for its collection URL returning that shape — copy the `widgets` OPTIONS handler's structure. This is what powers the `usage:`/`or:` synopsis and the detailed arg listing in `wrapido <namespace> <route>`.
3. Add GET/POST/PUT/DELETE handlers as needed, matching real WordPress response shapes closely enough for the CLI's formatting/field-extraction code to exercise realistically (e.g. `title: { rendered: ... }`, numeric `id`, error bodies shaped like `{ code, message, data: { status } }` — see `parseErrorResponse` in `core/errors.ts` for the exact shape it expects).
4. If mutating state (a `Map` like `widgets`), remember state persists **across tests in the same file** (the fixture is started once in `beforeAll`). Don't assume a fresh resource id in every test — either create your own resource inside the test (see the `createWidget()` helper in the `meta`/`generate`/`exists` `describe` blocks) or be explicit about which earlier test's side effects you're relying on (see the comment above the "delete-verb help" test about widget 2).
5. Match the `send(res, status, body)` / `readBody(req)` helpers already at the top of the file rather than reaching for `express` or another framework — this is deliberately a zero-dependency raw `http` server.

## Writing the test

- Where a test belongs depends on what it exercises, not file size — pick based on content, and re-profile (see below) if a file drifts badly out of balance:
  - Basic dispatch/CRUD/help/`--debug`/`--no-color` → `cli-core.test.ts`.
  - Nested/mid-path/two-parameter routes, singleton routes, `exists`, `generate` → `cli-core-routing.test.ts`. Both this and `cli-core.test.ts` define the same `run(args)` helper at the top of the file; it appends `--url=<fixture.baseUrl> --quiet --no-color` and sets `reject: false` (via the shared `runCli` in `test/integration/fixtures/run-cli.ts`), so check `result.exitCode`/`result.stdout`/`result.stderr` explicitly rather than relying on `execa` throwing.
  - `meta` subcommands → `cli-meta.test.ts`, under its `describe('meta', ...)` block — see its local `createWidget()` helper (a fresh-resource helper, since fixture state persists across tests in the same file) for the pattern if a new test needs its own widget.
  - Anything touching `src/config.ts`-persisted state (`wrapido auth`/`wrapido config`) → `cli-auth.test.ts` (Application Passwords + `config store recovery`) or `cli-auth-oauth2.test.ts` (`auth oauth2`), never `cli-core.test.ts`'s/`cli-core-routing.test.ts`'s top-level `run()` helper — that doesn't isolate the config store, so tests would read/clobber whatever real `wrapido` config exists on the machine running them. Follow the target file's own `runAuth(args)`/`runOAuth2(args)` pattern instead: a `beforeAll`/`afterAll`-scoped temp directory passed as `XDG_CONFIG_HOME` in `runCli`'s `env` option, isolating that block's config store per test run.
- Integration tests are slow (roughly 0.3–1s each now that they spawn the built `dist/cli.js` via `node` rather than `tsx`-transpiling `src/cli.ts`, still real subprocess overhead); group related assertions into one test rather than one `it()` per assertion where reasonable, but keep independent behaviors (success path vs. error path vs. `--format` variants) as separate `it()`s for clear failure attribution.
- Run just one file while iterating: `npx vitest run test/integration/cli-core.test.ts` (or any of the other four). Run one test by name: `npx vitest run test/integration/cli-core.test.ts -t "name substring"`. Either needs a prior `npm run build` if not run via `npm run test:integration` (whose `pretest:integration` hook builds automatically).
- The five-way split is balanced by *profiled time*, not line count or test count — if a file grows enough to noticeably dominate the others, re-check the balance with `npx vitest run --reporter=verbose 2>&1 | grep '✓ test/integration'` and move `describe` blocks between files (or split further) to keep each file in a similar time band, since Vitest's cross-file parallelism only helps as much as the slowest file allows.
